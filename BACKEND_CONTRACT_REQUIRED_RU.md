# Минимальный backend-контракт для первого личного чата

Чтобы WEB, Android и iOS могли начать личный чат с любым сотрудником без
предварительной общей переписки, каталог пользователей должен возвращать
серверную realtime-привязку:

```json
{
  "id": "backend-user-uuid",
  "login": "i.morozov",
  "realtime_user_id": "usrAbCdEfGhI12"
}
```

Допустимое совместимое имя поля — `tinode_uid`. WEB v25 понимает оба варианта
и повторно запрашивает профиль выбранного сотрудника непосредственно перед
созданием нового чата.
Значение необходимо брать из существующей таблицы `tinode_user_links`, а не
вычислять на клиенте и не искать по отображаемому имени.

Рекомендуемый минимальный вариант — добавить `LEFT JOIN tinode_user_links` в
read-only проекцию `/api/v1/users`. Правила видимости должны совпадать с
корпоративным каталогом: если роль видит сотрудника и имеет право начать с ним
чат, она получает его realtime ID.

Минимальная серверная проекция:

```sql
LEFT JOIN tinode_user_links l ON l.user_id = u.id
```

```sql
l.tinode_uid AS realtime_user_id
```

Если значение равно `null`, сотрудник ещё ни разу не активировал Tinode-профиль.
Клиент не должен создавать фиктивный локальный чат или вычислять `usr…` из UUID.

Для этой доработки не нужна новая миграция: таблица `tinode_user_links` уже
создана Stage 7A. Миграции `0003` и `0004` повторно не запускать,
`ciframigrate-staging` оставить остановленным.

Для полного текста в режиме аудита нужен отдельный согласованный read-only
compliance-контракт. Текущий `/api/v1/compliance/search` возвращает только
`topic_id`, `seq`, `sender_id`, `kind`, `created_at` и `deleted_at`; WEB не должен
пытаться расшифровывать или выдумывать содержимое самостоятельно.
