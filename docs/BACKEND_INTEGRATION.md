# Подключение CIFRA Messenger Web к бэкенду

## 1. Что сейчас находится в архиве

Интерфейс версии 11 полностью кликабельный, но работает как прототип:

- чаты — `initialChats`;
- сообщения — `initialMessagesByChat`;
- сотрудники — `initialUsers`;
- действия меняют React-state только в текущей вкладке;
- тема и глобальные уведомления сохраняются локально;
- звонок имитирует интерфейс, но не передаёт аудио/видео.

Это означает: дизайн и сценарии готовы, серверные данные нужно подключать
последовательно.

## 2. Целевая схема

```text
Браузер / PWA
  ├─ REST HTTPS ─────────────> CIFRA Gateway (Fastify)
  ├─ WebSocket WSS ──────────> CIFRA corporate events
  └─ Tinode WebSocket WSS ───> Tinode Server

CIFRA Gateway ──> PostgreSQL
CIFRA Gateway ──> PostgreSQL Outbox ──> Worker
Tinode Server ──> отдельная схема/БД Tinode в PostgreSQL
```

Браузер никогда не подключается напрямую к PostgreSQL, Worker или внутренним
секретам.

## 3. Что за что отвечает

| Компонент | Назначение |
| --- | --- |
| CIFRA Gateway | авторизация, MFA, пользователи, роли, медиа, настройки, аудит, корпоративные события |
| Tinode | чаты, сообщения, подписки, присутствие, доставка и чтение |
| CIFRA WebSocket | изменения ролей, блокировки, административные и корпоративные события |
| Worker | фоновые задачи и обработка событий PostgreSQL Outbox |
| PostgreSQL | постоянные данные; доступ только со стороны серверов |
| Frontend | интерфейс, локальное состояние формы, отображение серверных данных |

## 4. Переменные окружения frontend

Создайте `.env.local` на основе `.env.example`:

```env
NEXT_PUBLIC_DATA_MODE=mock
NEXT_PUBLIC_CIFRA_API_URL=https://api-stage.example.ru
NEXT_PUBLIC_CIFRA_WS_URL=wss://api-stage.example.ru/ws
NEXT_PUBLIC_TINODE_WS_URL=wss://tinode-stage.example.ru/v0/channels
CIFRA_SERVER_API_URL=http://cifra-gateway.internal:3000
```

Правила:

- frontend stage подключается только к backend stage;
- production подключается только к production;
- в production разрешены только `https://` и `wss://`;
- JWT, пароли, DATABASE_URL и ключи нельзя хранить в `NEXT_PUBLIC_*`;
- разрешите CORS только для точных адресов frontend stage/prod;
- проверяйте `Origin` при WebSocket-подключении.

## 5. Уже известная часть API-контракта

В текущем CIFRA Corporate API зафиксированы:

- `GET /health/live`;
- `GET /health/ready`;
- `GET /metrics` — не выводить напрямую в публичный браузер;
- `POST /api/v1/auth/login`;
- `POST /api/v1/auth/mfa/verify`;
- `POST /api/v1/auth/refresh`.

Тело входа:

```json
{
  "login": "employee",
  "password": "********",
  "device": {
    "id": "stable-browser-device-id",
    "name": "Chrome on Windows",
    "platform": "web"
  }
}
```

Ответы и остальные маршруты берите из актуального OpenAPI бэкенда. Не
придумывайте названия полей вручную: сгенерируйте TypeScript-типы из OpenAPI и
зафиксируйте версию контракта.

## 6. Правильный порядок интеграции

### Этап 1 — связь и health check

1. Запустите backend stage.
2. Укажите API/WS-адреса в frontend stage.
3. Вызовите `checkBackendReady()` из `lib/backend/client.ts`.
4. Проверьте HTTPS, WSS, CORS и отсутствие mixed content.

Готовность: `/health/ready` возвращает успешный ответ из браузера или через
same-origin frontend API.

### Этап 2 — авторизация и MFA

1. Сделайте настоящий экран входа.
2. Подключите `/auth/login`.
3. При требовании MFA откройте ввод кода и вызовите `/auth/mfa/verify`.
4. Обновляйте сессию через `/auth/refresh`.
5. После входа загрузите текущего пользователя и его серверную роль.

Безопасный вариант: refresh-токен хранится в `HttpOnly Secure SameSite` cookie,
а access-токен — короткоживущий. Не храните refresh-токен в `localStorage`.

### Этап 3 — пользователи и роли

Замените `initialUsers` запросами списка организации и профиля. Поиск должен
работать на сервере или по полученному разрешённому набору. Роли и право
администратора читать аудит всегда проверяются backend-ом; скрытая кнопка в UI
не является защитой.

### Этап 4 — чаты и сообщения через Tinode

Замените:

- `initialChats` — подписками/topics Tinode плюс корпоративные метаданные;
- `initialMessagesByChat` — историей сообщений с курсором;
- `sendMessage()` — публикацией через Tinode;
- `online` — presence-событиями;
- unread/read — серверными sequence/read markers.

Для каждого исходящего сообщения создавайте стабильный `client_message_id`.
Это предотвращает дубли при повторной отправке после потери сети.

### Этап 5 — беседы и участники

`memberIds` должен приходить из фактического состава беседы. Создание группы,
добавление/удаление участника и число пользователей онлайн выполняются на
сервере, после чего UI обновляется подтверждённым событием.

### Этап 6 — пользовательские настройки чатов

Закрепление, mute, архив и удаление — настройки конкретного пользователя.
Сохраните их на сервере и применяйте оптимистично:

1. UI сразу меняет строку;
2. отправляется запрос;
3. при ошибке состояние откатывается и показывается понятное сообщение.

Лимит трёх закреплённых чатов должен повторно проверяться backend-ом.

### Этап 7 — медиа и файлы

1. Получите серверный upload URL или вызовите media API.
2. Загрузите файл с отображением прогресса.
3. После подтверждения отправьте сообщение со ссылкой/идентификатором медиа.
4. На сервере проверьте размер, MIME, антивирус и права доступа.
5. Для видеокружков используйте FFmpeg в серверном media-процессе.

До масштабирования постоянные файлы можно хранить в `/data`; затем перейти на
S3-совместимое хранилище без изменения UI-контракта.

### Этап 8 — аудит администратора

Аудит загружается отдельным защищённым API. Нужны:

- проверка роли на backend;
- постраничная выдача;
- журнал факта просмотра;
- запрет редактирования из режима аудита;
- фильтрация удалённых чатов согласно корпоративной политике.

### Этап 9 — звонки

Текущая реализация — только UI. Для реальных звонков нужен отдельный
WebRTC/signaling-контур, TURN/STUN, разрешения камеры/микрофона и политика
групповых комнат. Не считайте звонки готовыми после подключения REST/Tinode.

### Этап 10 — мобильная надёжность

Перед iOS/Android production добавьте:

- cursor/resume sync после сна и потери сети;
- регистрацию device sessions;
- APNs/FCM push tokens;
- background upload;
- дедупликацию по `client_message_id`;
- нагрузочные тесты REST, WebSocket, медиа и восстановления.

## 7. Где менять текущий код

Сначала вынесите данные и действия из `app/page.tsx`:

```text
features/auth/
features/users/
features/chats/
features/messages/
features/media/
features/calls/
lib/backend/
```

На каждую область создайте интерфейс репозитория и две реализации:

- `mock` — сохраняет нынешний демонстрационный режим;
- `api` — вызывает CIFRA Gateway/Tinode.

Переключение выполняется через `NEXT_PUBLIC_DATA_MODE`. Так frontend можно
показывать и тестировать даже при временно выключенном backend.

## 8. Порядок запуска всего контура

1. PostgreSQL.
2. Одноразовые миграции.
3. Tinode.
4. CIFRA Gateway/API.
5. Worker.
6. CIFRA Web.

`pgAdmin` нужен только для диагностики. Миграционный сервис после успешного
выполнения может быть остановлен.

## 9. Критерии готовности интеграции

- после перезагрузки чаты, сообщения и участники не пропадают;
- один пользователь не видит чужие данные без права;
- MFA и refresh работают;
- два WebSocket восстанавливаются после сна/обрыва;
- сообщения не дублируются;
- unread/read синхронизируются на двух устройствах;
- mute/pin/archive сохраняются на сервере;
- удаление и аудит соответствуют ролям;
- медиа доступны только участникам;
- frontend stage не обращается к production;
- секретов нет в JavaScript bundle и GitHub.
